## P0 — Broken

### P0-1 · `Organization.logo` in homepage JSON-LD points to a nonexistent URL

**File:** `apps/web/app/page.tsx:133`
**Affected URL:** `/` (homepage)

The homepage emits a `WebSite` + `Organization` JSON-LD block. The `publisher.logo` field is hard-coded as:

```
logo: siteUrl() + '/icon-512.png',
```

No file named `icon-512.png` exists anywhere in the repo — not in `apps/web/public/`, not generated by any `app/icon.tsx` or `app/icon.png` convention. The existing icon assets are `app/icon.svg` (served as `/icon.svg`) and `app/apple-icon.tsx` (generates 180×180 at `/apple-icon`). The reference URL `https://cinecanon.com/icon-512.png` returns a 404 at runtime. Google's structured-data validator treats a logo that resolves to 404 as an invalid `Organization` block, which suppresses the Knowledge Panel brand logo and undermines the site's entity-disambiguation signal for AI crawlers (ClaimReview authority traces back to the Organization).

**Fix:** Either (a) add a 512×512 PNG to `apps/web/public/icon-512.png`, or (b) change the reference to a URL that resolves — the `/apple-icon` edge route generates 180×180 which is within Google's acceptable logo range, or (c) use the `@id`-only Organization reference without a logo until one is generated.

### P1-2 · 30+ `console.warn` / `console.error` calls in server-side production code paths

**Files:** ~20 `apps/web/app/*/page.tsx` files (sample below)

CLAUDE.md rule: "Don't add console.log or console.error in production code paths — use Sentry."

These calls appear in server components handling DB query failures via try/catch, where a missing or not-yet-migrated table causes a fallback to an empty state. Examples:

- `app/decisions/page.tsx:36` — `console.warn('[decisions] table missing', err)`
- `app/vfx/volumes/page.tsx:28` — `console.warn('[vp_volumes] table missing or query failed; rendering empty state', err)`
- `app/music/orchestras/page.tsx:24` — `console.warn('[recording_orchestras] table missing or query failed', err)`
- `app/partnerships/page.tsx:24` — `console.warn('[partnerships] table missing or query failed', err)`
- `app/costume-hair-makeup/effects-houses/page.tsx:24` — `console.warn('[makeup_effects_houses] table missing', err)`
- `app/page.tsx:79-80` — `console.error('[homepage] listRecentlyResolvedCorrections failed', e)` and `listRecentCitations failed`
- Plus 20+ additional occurrences across sound, stunt, VFX, gear, and music sub-pages

When these DB queries fail on production, the failures are logged to Vercel Function log output but are NOT captured by Sentry. Ops cannot triage them via the error dashboard. Additionally, `console.error` on the homepage means homepage fetch failures are invisible to alerting.

### P1-3 · `EvidenceGallery` serves content images with `alt=""`

**File:** `apps/web/components/ui/EvidenceGallery.tsx:29`

Evidence items are BTS stills, frame grabs, or reference scans used as visual proof of editorial claims (the core of CineCanon's credibility). The component renders:

```tsx
<img src={mediaUrl} alt="" className="aspect-video w-full object-cover opacity-90" loading="lazy" />
```

When `item.caption` is populated (the expected case for curated evidence), the caption is displayed as adjacent text below the image, but the image itself carries no alt text. This is a WCAG 1.1.1 violation for content images: screen-reader users lose the visual evidence entirely. The fix is `alt={item.caption ?? item.source_title ?? 'Evidence image'}`.

### P1-4 · Missing `<link rel="canonical">` on 20+ pages that appear in the sitemap

**Files:** Multiple `apps/web/app/*/page.tsx`

The following pages are present in `sitemap-core.xml` but have no `alternates.canonical` in their metadata exports, meaning Next.js emits no `<link rel="canonical">` tag in the rendered HTML:

- `/ask` (`app/ask/page.tsx` — has `title` and `description` but no `alternates`)
- `/format` (`app/format/page.tsx`)
- `/stunts` and all five stunts sub-index pages (`/stunts/people`, `/stunts/sequences`, `/stunts/lineage`, `/stunts/rigging`, `/stunts/safety`)
- `/tools` and four tool pages: `/tools/frame-lines`, `/tools/coverage`, `/tools/cdl`, `/tools/aces`, `/tools/loadout`
- Utility pages: `/crew/compare`, `/films/compare`, `/gear/compare`, `/import/letterboxd`, `/search`, `/signin`

Without a canonical tag, search engines treat any URL variant (e.g., with query params like `?sort=recent` or `?tier=curated`) as potentially distinct. For filter-driven pages like `/films` and `/stunts/sequences`, duplicate content pressure is moderate but real.

Note: `/films`, `/crew`, `/vfx`, `/about` correctly use relative path canonicals (e.g., `alternates: { canonical: '/films' }`), which are resolved by Next.js via the `metadataBase` in `app/layout.tsx`. That pattern is fine. The issue is pages with NO canonical at all.

### P1-5 · VFX house detail pages can render with no `<meta name="description">`

**File:** `apps/web/app/vfx/[slug]/page.tsx:28`

```ts
const description = data.house.tagline ?? data.house.summary?.split('\n')[0]?.slice(0, 160) ?? undefined;
```

If a VFX house row has `tagline = null` and `summary = null` (which is possible for recently seeded or imported VFX house records), `description` is `undefined`, and the metadata object emits no description tag. The same pattern affects `dossiers/[slug]` when the dossier has no description field: `generateMetadata` falls through to `{ title: 'Dossier' }` with no description.

### P2-4 · Canonical URL format is inconsistent across pages

80+ pages use absolute canonicals: `alternates: { canonical: \`${siteUrl()}/films\` }`. 11 pages use relative paths: `alternates: { canonical: '/films' }`. Both work because `metadataBase` in the root layout resolves relative paths. But the inconsistency is a maintenance risk: if `metadataBase` is ever removed or misconfigured, the relative-path pages lose their canonicals silently.

Affected relative-canonical pages: `/`, `/films`, `/crew`, `/vfx`, `/about`, `/queries` (all three query pages), `/vfx/[slug]`, `/societies/[slug]`.

### P2-5 · 24 `next/Image` components carry `unoptimized` flag, including TMDb poster images

**Files:** `components/productions/ProductionCard.tsx`, `components/productions/ProductionDetail.tsx` (multiple instances), `components/productions/MediaGallery.tsx`, `components/people/FilmographyTable.tsx`, and 8 more.

The `unoptimized` flag bypasses Vercel Image Optimization (no WebP conversion, no responsive-size negotiation). This is intentional for keyframe images from arbitrary publisher CDNs (the reason documented in `next.config.mjs:41`). However, it is applied indiscriminately to TMDb posters and backdrops, which come from `image.tmdb.org` — a domain already listed in `remotePatterns`. TMDb posters on the production detail page (`ProductionDetail.tsx:276`) and production card (`ProductionCard.tsx:74`) are prime candidates for optimization: they appear on every film listing and detail page, likely the highest-traffic image class on the site.

### P2-6 · `MediaGallery` backdrop images lack production-title alt text

**File:** `apps/web/components/productions/MediaGallery.tsx:34`

The horizontal backdrop strip renders TMDb backdrop images as `alt=""`. Backdrop images show distinctive visual content from specific productions; screen-reader users receive no indication of what they show. ## What to Fix First

The single highest-leverage fix is the sitemap gap (P1-1): with 55+ indexed pages absent from the sitemap, every hour the site runs without them is an hour Google allocates crawl budget to the smaller known surface, leaving the awards, sound, music, editing, production-design, costume, role-landing, and tool pages entirely dependent on link-following. Add a sixth segment sitemap — `sitemap-departments.xml` — to `sitemap.xml/route.ts`, and populate it with static entries for all department index pages, the for-* role pages, the four Phase-4 tools, /about, /methodology, /awards, and /decades. That single route file (~60 URL entries) would immediately make the full public surface visible to Googlebot.

Simultaneously, resolve the `icon-512.png` 404 (P0-1) by adding a 512×512 PNG to `apps/web/public/`, since it damages the homepage's Organization structured data and the only fix is a static file copy. The EvidenceGallery alt-text (P1-3) and the console.warn/error instrumentation (P1-2) are the next highest-impact changes: the former is a live accessibility failure on claim-evidence images, and the latter means DB-layer errors on the decisions, partnerships, orchestras, and VP volumes pages are currently invisible to Sentry monitoring.
