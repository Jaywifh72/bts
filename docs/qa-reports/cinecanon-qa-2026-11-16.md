## P0 — Broken

### P0-1 — JSON-LD Organization logo URL is a 404

**File:** `apps/web/app/page.tsx:133`

```
logo: siteUrl() + '/icon-512.png',
```

The homepage's `Organization` JSON-LD block references `/icon-512.png` as the publisher logo. No such file exists in the repository and no Next.js route generates it. The only icon files in the app are `app/icon.svg` (served as `/icon.svg`; Next.js also generates `/icon.png` from it, but not `/icon-512.png`) and `app/apple-icon.tsx` (served as `/apple-icon.png`). Google Search Console uses the `Organization.logo` URL for Knowledge Panel construction; a broken 404 logo can suppress or demote the Knowledge Panel and downgrades the structured-data confidence score. This also affects AI crawlers (Perplexity, ChatGPT, Gemini) that read ClaimReview blocks and cross-reference the publisher entity.

**Fix:** Either change the reference to `/icon.png` (auto-generated by Next.js from `icon.svg`) or add an `app/icon-512/route.ts` that returns a 512×512 PNG rendered via Satori/ImageResponse.

### P1-2 — `console.error` / `console.warn` in 35 production code paths

**Files (sample):** `apps/web/app/page.tsx:79-80`, `apps/web/app/sound/page.tsx`, `apps/web/app/vfx/volumes/page.tsx`, `apps/web/app/partnerships/page.tsx`, `apps/web/app/dossiers/[slug]/page.tsx`, `apps/web/app/api/search/nl/route.ts`

CLAUDE.md explicitly states: "Don't add console.log or console.error in production code paths — use Sentry." There are 2 `console.error` and 33 `console.warn` calls in production route handlers and page components:

- `app/page.tsx:79-80` — two `console.error` calls inline in Promise chains for homepage DB queries. These are especially concerning because they fire on every homepage render where the DB call soft-fails, flooding server logs.
- `app/api/search/nl/route.ts:78` — `console.error` on embedding failure.
- Multiple pages (`sound/adr-studios`, `vfx/volumes`, `partnerships`, `dossiers`, `gear/rentals`, `music/orchestras`, `music/supervision-agencies`, `sound/effects/libraries`, `editing/walkthroughs`, `vfx/shot-breakdowns`, `vfx/title-houses`, `production-design/works`, `costume-hair-makeup/construction-houses`, `costume-hair-makeup/costume-works`, `sound/foley`, `sound/effects`, `sound/post`, `sound/houses`, `sound/effects/libraries`, `sound/adr-studios`, `sound/mixers`, `sound/designers`, `music/scoring-stages`, `music/cue-guides`) use `console.warn` to swallow errors from DB queries that may fail when a migration has not yet been applied.

The `console.warn` pattern is used as a "defensive try/catch" for schema-not-ready scenarios, which is a valid recovery pattern but should route through `Sentry.captureException` with tagged context, not `console.warn`, so the operator sees the signal.

### P1-6 — 13 public pages missing explicit canonical tags

**Pages:** `/stunts`, `/stunts/people`, `/stunts/lineage`, `/stunts/sequences`, `/ask`, `/gear`, `/format`, `/societies`, `/search`, `/tools`, `/tools/cdl`, `/tools/frame-lines`, `/tools/coverage`

These pages define `export const metadata` with `title` and `description` but no `alternates.canonical`. With `metadataBase` set in `layout.tsx`, Next.js generates canonical URLs from the URL path, so non-query-string URLs are correct. However:
- `/ask?q=...` and `/search?q=...` — search result pages that accept query params have no canonical pointing back to the base path, so each unique query string is a potential duplicate-content URL with its own self-referencing canonical.
- `/gear`, `/tools`, `/stunts` pages with filter query strings face the same issue.

### P2-4 — `NEXT_PUBLIC_SITE_URL` undocumented in `.env.example`

**File:** `apps/web/.env.example`

The variable `NEXT_PUBLIC_SITE_URL` is used throughout the codebase for canonical URLs, JSON-LD `@id` values, sitemap `<loc>` entries, and robots.txt `host`. Without it, `siteUrl()` falls back to `http://localhost:3000`. The `.env.example` file documents Auth.js variables but not `NEXT_PUBLIC_SITE_URL`. Any new deployment environment that doesn't discover this variable via Vercel's existing settings would emit localhost-based canonical URLs to search engines.

### P2-7 — `console.warn` used as error-swallowing pattern for missing-table scenarios

**Files:** 28 files in `apps/web/app/` — including `sound/adr-studios`, `vfx/volumes`, `partnerships`, `dossiers/[slug]`, `gear/rentals`, `music/orchestras`, `music/supervision-agencies`, and many more.

The pattern `try { rows = await query(); } catch (e) { console.warn('[section] table missing', e); }` is used to gracefully degrade when a migration has not yet been applied. While the defensive pattern is correct (and was noted in CLAUDE.md as intentional), routing through `console.warn` means the signal never reaches Sentry. If a production deployment rolls back a migration, these silent `console.warn` calls would be the only signal — invisible to the error dashboard.

## What I'd Fix First

The single highest-leverage fix is expanding `sitemap-core.xml` to include the 65 missing public routes — specifically the Phase 4 tools, all 12 for-working-pros pages, and the department indexes (/sound, /music, /editing, /costume-hair-makeup, /production-design). These are the surfaces the AEO/GEO strategy (CineCanon-Sentinel) depends on for AI engine citation, yet they are invisible to sitemap-driven crawlers. That fix takes under 30 minutes in `apps/web/app/sitemap-core.xml/route.ts`. Immediately after, fix the broken `/icon-512.png` reference in the homepage JSON-LD (change to `/icon.png`) — it takes one line and prevents Google from downgrading the Knowledge Panel publisher entity. Third, route the 35 `console.warn`/`console.error` calls in production code through `Sentry.captureException` so the team actually sees when DB queries silently fail in production, since the defensive try/catch pattern is correct but the logging destination is wrong.
